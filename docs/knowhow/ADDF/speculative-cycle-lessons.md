# 投機サイクル運用の教訓

> 出典: `/loop 1h /addf-speculate` の1周（4本並列 → 1本衝突で整合できず外す → 3本統合 → 3ペルソナレビュー → 修正指示 → 再統合）。手順設計の外側で見えてきた運用上の教訓を記録する。

## 発見した知見

### 1. 「単体では動くが統合すると意図が衝突する」パターン — 選定時の兆候と統合時の対処

投機は「触るファイル集合の重なりゼロ」だけで独立性を担保できない。**意味論の変更が同じ AST 層に載る**場合、単体テストは通っても統合時に片方のテストがもう片方の変更で失敗する。

**兆候（選定時に検出したい）**:
- 対象概念が同じレイヤー（例: shell topology のワード抽出）のセマンティクスを触る
- 両者とも「何を静的とみなし、何を動的とみなすか」の判定に手を入れる
- 一方は「入力を厳格化」（クォート除去）、他方は「検出を厳格化」（動的展開の再帰検出）— 順序と粒度で挙動が変わる

**統合時の対処**:
- 単体レイヤーの回帰テストが「入力にクォートが残っている前提」で書かれていると、統合時に無条件で落ちる → **入力の前処理をテストで模してから検出テストを書く**（クォート除去済み入力・生入力の両方をカバー）
- それでも整合できないなら諦めて `衝突` で外す。「単体で動くから」を根拠に統合を強行しない
- 外した側はブランチを push して保存し、Dashboard の「気になった点」で採否判断をオーナーに委ねる。**silent に破棄しない**

**一般化**: 直交性は「ファイル集合の重なり」ではなく「意味論の同一 AST 層への干渉」で見る。同層を触る投機は原則1本に絞るか、片方を後日 rebase 前提で「先送り」にする。

### 2. 3ペルソナ並列レビューは「本 PR 起因ではない既存バグ」を掘り当てる — 分離してオーナー起票判断に回す

skeptic/attacker/newcomer の視点ずらしレビューは、本 PR の変更がまさに解こうとした脅威モデルの**兄弟パターン**（同じクラスの既存バグ）を高確度で検出する。

- **例1**: 「クォートによるルール名バイパス（`"rm" -rf /`）」を塞ぐ変更に対し、attacker が「バックスラッシュエスケープ（`\rm`, `-X POS\T`）」を実証（`main` にも存在する既存バグ、実行時は bash が unescape）
- **例2**: 同じレビューで「DblQuoted 内の動的展開が Analyzable=true になる（`"$(cmd)" -rf /`）」も浮上（既存バグ）
- **例3**: skeptic が新設した `scope_violation: deny` の3経路バイパス（warn/hint/fallback: allow）を段階比較の欠如として指摘（本 PR 起因、その場で修正）

**運用の分離ルール**:
- **本 PR 起因の Critical/Warning** → 投機フローの品質ゲート内で担当エージェントに修正を1周依頼。それでも通らなければ「テスト失敗」で打ち切り
- **既存バグ（`main` にも存在するクラス）** → 投機の範疇外。Dashboard の「気になった点」に列挙し、優先度案を添えて**新 Plan 起票の判断をオーナーに委ねる**。投機は使い捨てが原則、既存バグを深追いすると投機の意義（軽量な残課題の消化）を逸脱する
- **ドキュメントドリフト** → 投機起因のもの（新設コメントが英日不一致を参照 等）は本サイクルで修正。既存のドリフトは Dashboard 送り

**Progress.md 運用ルール7の「Critical/High 先送り禁止」との整合**: 「先送り禁止」は本タスクが**触ったコード**が生む Critical。「本タスク以前から存在する既存バグ」は同じ強制の対象ではない（バグ分離ルール — Progress.md 7 の「関心事が異なる場合は新 Plan」と同じ思想）。

### 3. 兄弟課題は同一投機ブランチに束ねる — 別ブランチに切ると非対称な穴を残す

同じ AST 層で「クォート除去」と「バックスラッシュエスケープ処理」は、実 bash では**同じ字句解析フェーズで並行して起きる**。しかし今サイクルは:

- `args-hardening` にクォート除去だけ入れた
- バックスラッシュエスケープは「本 PR の範囲外」として据え置いた

結果、`"rm" -rf /` は塞がったが `\rm -rf /` は素通りする**非対称な防御**が生まれた。攻撃者は塞がれた側を諦めて開いている側を使うだけで、防御コストは増えたのに攻撃コストはほぼ変わらない。

**選定時のチェック**:
- 対象概念が「複数の兄弟入力パターン」に対する同じ処理を要求するとき、片方だけを実装すると**残りが実質的な回避経路**として残る
- 選定元の Plan が「1点だけ」を残課題として挙げていても、実装者（AI）は隣接する兄弟パターンを能動的に列挙して同一ブランチに含めるべきか判断する
- 兄弟をすべて塞げないなら、**ドキュメントで既知の限界を明記**して「実装済み範囲」を過大主張しない（今サイクルは `docs/reference/dsl.md` に限界を追記した）

**判断のヒューリスティック**: 「もし攻撃者が塞がれた入力を諦めたら、代わりに何を使うか」を1つ挙げてみる。挙がったものがコード的に隣接しているなら同一ブランチに含める。

## プロジェクトへの適用

- `/addf-speculate` 手順2（投機対象の選定）と手順7（Stage 2）の運用指針を補強する
- 選定時: 「触るファイル集合の重なり」だけでなく「意味論の同一 AST 層への干渉」もチェック（知見1）
- 選定時: 「兄弟パターンを列挙して同一ブランチに含めるか」を検討（知見3）
- Stage 2 のペルソナレビュー結果は「本 PR 起因」と「既存バグ」に分離してから修正 vs Dashboard 送りを決める（知見2）

## 注意点・制約

- 3ペルソナ並列（skeptic/attacker/newcomer）は unattended モードで発動条件を満たす（Progress.md 5 のペルソナ並列規定）。通常タスクでは単体レビューでよい — このノウハウはペルソナ並列時の**指摘のさばき方**であり、常時 3 体並列を推奨するものではない
- 「既存バグを Dashboard に流す」は投機だからこそ許される運用。本流の実装フェーズでは「同じコードパスに触った」時点で既存バグの修正責任も引き受けるのが基本
- 兄弟課題の同一ブランチ化は「投機の粒度＝1概念」原則と衝突しない — 兄弟は**同じ概念の複数の入力パターン**であって、複数概念ではない
