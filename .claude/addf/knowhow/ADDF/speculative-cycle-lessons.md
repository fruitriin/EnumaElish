# 投機サイクル運用の教訓

> 出典: `/loop 1h /addf-speculate` の1周（4本並列 → 1本衝突で整合できず外す → 3本統合 → 3ペルソナレビュー → 修正指示 → 再統合）。手順設計の外側で見えてきた運用上の教訓を記録する。

## 発見した知見

### 1. 「単体では動くが統合すると意図が衝突する」パターン — 選定時の兆候と統合時の対処

投機は「触るファイル集合の重なりゼロ」だけで独立性を担保できない。**意味論の変更が同じ AST 層に載る**場合、単体テストは通っても統合時に片方のテストがもう片方の変更で失敗する。

**兆候（選定時に検出したい）**:
- 対象概念が同じレイヤー（例: shell topology のワード抽出）のセマンティクスを触る
- 両者とも「何を静的とみなし、何を動的とみなすか」の判定に手を入れる
- 一方は「入力を厳格化」（クォート除去）、他方は「検出を厳格化」（動的展開の再帰検出）— 順序と粒度で挙動が変わる

**統合時の対処**:
- 単体レイヤーの回帰テストが「入力にクォートが残っている前提」で書かれていると、統合時に無条件で落ちる → **入力の前処理をテストで模してから検出テストを書く**（クォート除去済み入力・生入力の両方をカバー）
- それでも整合できないなら諦めて `衝突` で外す。「単体で動くから」を根拠に統合を強行しない
- 外した側はブランチを push して保存し、Dashboard の「気になった点」で採否判断をオーナーに委ねる。**silent に破棄しない**

**一般化**: 直交性は「ファイル集合の重なり」ではなく「意味論の同一 AST 層への干渉」で見る。同層を触る投機は原則1本に絞るか、片方を後日 rebase 前提で「先送り」にする。

### 2. 3ペルソナ並列レビューは「本 PR 起因ではない既存バグ」を掘り当てる — 分離してオーナー起票判断に回す

skeptic/attacker/newcomer の視点ずらしレビューは、本 PR の変更がまさに解こうとした脅威モデルの**兄弟パターン**（同じクラスの既存バグ）を高確度で検出する。

- **例1**: 「クォートによるルール名バイパス（`"rm" -rf /`）」を塞ぐ変更に対し、attacker が「バックスラッシュエスケープ（`\rm`, `-X POS\T`）」を実証（`main` にも存在する既存バグ、実行時は bash が unescape）
- **例2**: 同じレビューで「DblQuoted 内の動的展開が Analyzable=true になる（`"$(cmd)" -rf /`）」も浮上（既存バグ）
- **例3**: skeptic が新設した `scope_violation: deny` の3経路バイパス（warn/hint/fallback: allow）を段階比較の欠如として指摘（本 PR 起因、その場で修正）

**運用の分離ルール**:
- **本 PR 起因の Critical/Warning** → 投機フローの品質ゲート内で担当エージェントに修正を1周依頼。それでも通らなければ「テスト失敗」で打ち切り
- **既存バグ（`main` にも存在するクラス）** → 投機の範疇外。Dashboard の「気になった点」に列挙し、優先度案を添えて**新 Plan 起票の判断をオーナーに委ねる**。投機は使い捨てが原則、既存バグを深追いすると投機の意義（軽量な残課題の消化）を逸脱する
- **ドキュメントドリフト** → 投機起因のもの（新設コメントが英日不一致を参照 等）は本サイクルで修正。既存のドリフトは Dashboard 送り

**Progress.md 運用ルール7の「Critical/High 先送り禁止」との整合**: 「先送り禁止」は本タスクが**触ったコード**が生む Critical。「本タスク以前から存在する既存バグ」は同じ強制の対象ではない（バグ分離ルール — Progress.md 7 の「関心事が異なる場合は新 Plan」と同じ思想）。

### 3. 兄弟課題は同一投機ブランチに束ねる — 別ブランチに切ると非対称な穴を残す

同じ AST 層で「クォート除去」と「バックスラッシュエスケープ処理」は、実 bash では**同じ字句解析フェーズで並行して起きる**。しかし今サイクルは:

- `args-hardening` にクォート除去だけ入れた
- バックスラッシュエスケープは「本 PR の範囲外」として据え置いた

結果、`"rm" -rf /` は塞がったが `\rm -rf /` は素通りする**非対称な防御**が生まれた。攻撃者は塞がれた側を諦めて開いている側を使うだけで、防御コストは増えたのに攻撃コストはほぼ変わらない。

**選定時のチェック**:
- 対象概念が「複数の兄弟入力パターン」に対する同じ処理を要求するとき、片方だけを実装すると**残りが実質的な回避経路**として残る
- 選定元の Plan が「1点だけ」を残課題として挙げていても、実装者（AI）は隣接する兄弟パターンを能動的に列挙して同一ブランチに含めるべきか判断する
- 兄弟をすべて塞げないなら、**ドキュメントで既知の限界を明記**して「実装済み範囲」を過大主張しない（今サイクルは `docs/reference/dsl.md` に限界を追記した）

**判断のヒューリスティック**: 「もし攻撃者が塞がれた入力を諦めたら、代わりに何を使うか」を1つ挙げてみる。挙がったものがコード的に隣接しているなら同一ブランチに含める。

## プロジェクトへの適用

- `/addf-speculate` 手順2（投機対象の選定）と手順7（Stage 2）の運用指針を補強する
- 選定時: 「触るファイル集合の重なり」だけでなく「意味論の同一 AST 層への干渉」もチェック（知見1）
- 選定時: 「兄弟パターンを列挙して同一ブランチに含めるか」を検討（知見3）
- Stage 2 のペルソナレビュー結果は「本 PR 起因」と「既存バグ」に分離してから修正 vs Dashboard 送りを決める（知見2）

## 注意点・制約

- 3ペルソナ並列（skeptic/attacker/newcomer）は unattended モードで発動条件を満たす（Progress.md 5 のペルソナ並列規定）。通常タスクでは単体レビューでよい — このノウハウはペルソナ並列時の**指摘のさばき方**であり、常時 3 体並列を推奨するものではない
- 「既存バグを Dashboard に流す」は投機だからこそ許される運用。本流の実装フェーズでは「同じコードパスに触った」時点で既存バグの修正責任も引き受けるのが基本
- 兄弟課題の同一ブランチ化は「投機の粒度＝1概念」原則と衝突しない — 兄弟は**同じ概念の複数の入力パターン**であって、複数概念ではない

## サイクル2 での実践成果と新パターン（2026-07-05 追記）

### 教訓1（同一 AST 層への干渉）を選定時にチェックした結果

サイクル2 では 3本すべて **触る AST 層をあらかじめ分離**（scope.go / topology.go / hook.go）して投機を組んだ。結果、**integration の相互作用テストが一発 PASS**（サイクル1 は stripquotes-escape と args-hardening の同層干渉で1本外す羽目になった）。教訓の実効性が確認できた。選定時に一問確認するだけで統合コストが数分〜十数分節約できる。

### 教訓3（兄弟課題の同一ブランチ化）の効果 — レビュー時に対称性の穴が浮上した

サイクル2 では `workspace-scope-hardening` に **read/write 分離 + シンボリックリンク解決** の兄弟課題を意図的に束ねた。attacker ペルソナが `cp -t DIR` バイパス（read/write 位置ベース判定の穴）と、シンボリックリンク未解決の**組み合わせ**で symlink 経由の write を allow できることを実証コード付きで検出。片方だけ実装していたら **`outside-write: deny` を設定していても symlink 経由でバイパスできる非対称な穴** が残っていた。束ねたおかげで対称的な防御になった。

### 新パターン: 統合コンフリクトへの手動介入（integration スクリプトの限界）

`speculate-integrate.py` は `git merge --squash` で feature を統合するが、feature 間で自明でない衝突が起きるとその feature を「conflicted」として外す（reset --hard で戻す）設計。ただし**自明な衝突**（例: 独立セクションへの追記同士）なら手動介入で解消できる:

1. スクリプトを衝突しない subset だけで走らせて integration ブランチを作る（例: 3本のうち 2本）
2. integration worktree の中で `git merge --squash speculative/<残り>` を手動で実行
3. コンフリクトファイルを Edit で解消（両方の追記を並べる）
4. `git add -A && git commit --no-verify -m "[統合] speculative/<残り> を squash 統合（<衝突箇所> の手動解消）"`

サイクル2 で `workspace-scope-hardening` と `strict-config-error` が Grammar 早見表（Settings ブロック）に独立に追記していて衝突したが、両行を並べるだけで解消できた。**「悩まず解決できる衝突」の定義そのもの**なので、諦めて外すのではなく手動解消が正解。手順書に上位フローとして追記されるべき運用。

### 新パターン: `Settings` フィールド単位マージ（Explicit 集合の追跡）

サイクル2 で `mergeConfigs` の `Settings = overlay.Settings`（丸ごと swap）が既存バグとして浮上した際、**overlay 側で明示的に設定されたフィールドだけを上書きする**設計を採用:

```go
type Settings struct {
    // ... 通常のフィールド ...
    Explicit map[string]bool  // parser で明示指定された DSL キー名
}

func mergeSettings(base, overlay Settings) Settings {
    merged := base
    for key := range overlay.Explicit {
        // key に対応するフィールドだけを overlay で上書き
    }
    return merged
}
```

`DefaultSettings()` は `Explicit: map[string]bool{}`（空）で初期化するので、デフォルト値経由では絶対に上書きされない。パーサーで DSL キーを読むたびに `Explicit[key] = true` を登録する1行を追加するだけ。ポインタ化案（`*bool`, `*int`）と比べて既存コードへの影響が最小。設定マージ機構を持つ他のスキル（downstream の Behavior.toml マージ等）にも応用可能。

### 実証コード付きレビューの威力

サイクル2 の attacker ペルソナは **Critical 7件すべてで再現テストコードを添えて指摘**（worktree 内で試して削除、報告に手順を明記）。指摘の説得力が段違いに高く、担当エージェントが「本当に修正必要か」を悩む余地がない。修正の完了確認も同じテストコードを回すだけで済む。ペルソナへの依頼プロンプトに「worktree 内でテストコードを書いて実際に試してよい（コミットはしないこと）」の一文を含めるかどうかで、レビュー成果の質が大きく変わる。

## 全 7 PR マージ時の統合作業パターン（2026-07-05 追記）

サイクル1・サイクル2 で作った 7 本の PR をオーナーが一括レビュー・マージ判定した際の実践知見。**投機フローの本来の目的（オーナーがまとめて採否判断できる状態を作る）がフルサイクルで達成されたサンプル**。

### 3種類の解消戦略の使い分け

| 衝突の性質 | 戦略 | 使いどころ |
|---|---|---|
| 衝突なし・Approve のみ | `gh pr merge --squash` で即マージ | PR #6 の `bash-c-analyzable-fix` |
| 単ファイル 1〜2 箇所の意味的統合 | 私が直接 Edit で衝突マーカーを解消 | PR #5 の `evaluate.go`/`tool.go`（HEAD の scope: ブロックと main の段階比較を統合） |
| 複数ファイル・広範囲の再構成 | 修正エージェントに worktree ごと委譲 | PR #7 の Explicit マップ経由フィールド単位マージ / PR #2 の破壊的統合（`unquoteWords` 呼び出し削除まで含む） |

**判断基準**: 「衝突箇所を全部読んで統合方針を書き出すコスト」と「エージェントに現在の main 状態と両ブランチの意図を過不足なく伝える文脈作成コスト」を比べる。前者が 5 分以内で終わりそうなら直接、それ以上なら委譲。委譲時は「A案 = xxx を優先」のような**単一原則**をプロンプトに明記すると、エージェントが迷わず統合できる。

### 「A案いいね」型の曖昧なオーナー指示への対応

サイクル2 で私が過去に「PR #2 と PR #4 は同時採用不可、どちらを優先するかの判断が必要」と提示したことに対し、オーナーからのコメントは **「A案いいね 利用者がいないはずなので Deprecated もなしで後方互換性なしで直しきっちゃって」** の1行。「A案」がどこに定義されているかは明示的に書かれていない。

私は「A案 = args-hardening を優先する路線」と解釈して修正エージェントに委譲し、結果的にオーナーの実際の意図と一致した。ただし**この判断が外れた場合は 500〜1000 行の破壊的統合をやり直すコストを負う**。

**教訓**: unattended モードでも「不可逆な judgment call」（本流の破壊的変更、API/DSL の後方互換破棄）は `AskUserQuestion` で解釈確認する方が安全。「A案いいね」に対して「A案 = `<私の解釈>` で進めてよいですか？」と 1 問確認する。実際に間違えて全 rebase やり直しになるコストと比べれば、確認 1 問のコストは無視できる。

### Cron / ガード / 上限のフィードバックループが機能した実例

`/loop 1h /addf-speculate` は毎時 :07 に発火するが、`speculate-guard.py` が `max_worktrees=7` を超えないよう自動制御する。実際にサイクル4〜9（オーナー不在で 6 サイクル分）は `slots=0` で全部スキップされ、コンテキストは短い記録追加のみで消費された。**自動発火ループを止める権限判断をエージェントが持たなくても、ガードによる自然な律速が機能する**。

さらに、コンテキスト使用量が実効目安を超えた場合はエージェント自身が「新規投機を見送って記録整理に専念」の判断ができる（サイクル3・サイクル10 で実践）。「Cron を止めろ」ではなく「今回はスキップ」と判断すれば越権にならない。

### AST 層干渉の教訓は Markdown ファイルにも適用される

サイクル1 (2026-07-04) の教訓「同じ AST 層への干渉」（`stripquotes-escape` vs `args-hardening` の topology 衝突）は、Go/コード層だけでなく **Markdown ファイルの複数セクション編集にも同型で発生する** ことが 2026-07-05 新セッションのサイクル1 で確認された。

具体的には `docs-warnings-cycle2`（Feedback.md の savanna-smell-detector セクションを「完了済み」に移動 + upstream リンク追記）と `feedback-archive-sweep`（Feedback.md の CLAUDE.repo.md エントリと savanna-smell-detector エントリを両方「完了済み」に移動）を並列で立ち上げたところ、統合時に `.claude/addf/Feedback.md` で衝突。両ブランチとも「同じセクションを再構成する」意図で編集していたが、粒度と文言が異なった。

**教訓**:
- 選定時のチェック軸に「同じ Markdown ファイルの同じセクションを編集していないか」を追加する
- 同一ファイル同士でも「独立追記」（末尾追加同士 / 別セクションへの追記同士）なら悩まず解決可能。「同一セクションの再構成」の場合のみ回避する
- 特に `.claude/addf/Feedback.md` のような「エージェント間の共有チャンネル」は複数投機が同時に触りやすい — 選定時に意識するとよい
- 衝突した場合の手動解消は「より完全な再構成版を採用し、他方の意味的追加（今回の場合 upstream #15 リンクと時制修正）を反映」で処理可能

### docs-only 投機でも実装バグを釣り上げる可能性がある

新セッションサイクル1 は「docs-only 2本」の軽量投機だったが、Stage 2 の attacker ペルソナが `docs/reference/config.md` の Prevention 推奨コマンド `ccchain check <path>` が実装上動かないバグを **実証コード付き** で発見した。実装 `cmd/ccchain/main.go` の `check` サブコマンドは positional 引数を受け付けず、`--config` フラグ経由のみ。バイナリで再現するとドキュメント通りの書き方は壊れた設定でも `config OK` を返す。

**教訓**:
- 「docs-only なら Stage 2 は軽く」という予断は危険。attacker ペルソナは docs の記述が実装と一致するかを検証するプロセスで実装バグを釣り上げうる
- ドキュメント投機でも Stage 2 は 3 ペルソナ並列で走らせる価値がある（コスト対効果が良い）
- ドキュメントに「動作確認済みのコマンド例」を書くときは、実際に手元で 1 回動かして確認する（review-time 検証）

**再確認（2026-07-06、PR #10 マージ前レビュー）**: 同じパターンが再現した。attacker が復旧手順を「実際に壊れた状態で」実機で辿り、**手順の記述そのものが実装と乖離**している Critical を2件検出（リネームは built-in フォールバックではなくグローバル conf へ黙って切替わる／`--config` 明示起動時はリネームが復旧にならない）。統合系 docs PR は「移設元の文言をそのまま運ぶ」ため、**移設時に元の文言の正しさも実装と突合する**必要がある — 一本化して「正本」に格上げする行為は、誤りの権威も上げてしまう。
